# Proposed feedback to ITU LVC and LearnCard

These are draft contributions for discussion, **not issues or messages already sent**. Evidence comes from ITU material retrieved on 14 October 2026, LearnCard repository commit `1de9e4a8aed6a03b9428a6fa7895c9681e50ea7e`, and the named npm releases. Check the latest upstream version and existing issues before filing. Our cloud-preview access failures and our custom backup limitations are primarily our delivery/application responsibilities, not evidence that either upstream specification is defective.

## Cover note for ITU

We built an adult learner-held education credential demonstration against the LVC-3 working draft using LearnCard issuance and independent Digital Bazaar verification. The distinction between cryptographic validity, credential status, issuer authority at issuance and recognition policy was especially useful. The main obstacle to reproducible interoperability was the absence of a fully specified implementation/test profile: independently reasonable choices about education schema, transport, status freshness and trust governance can still produce incompatible systems.

Please consider a small versioned reference profile and executable test pack before expanding the catalogue of options. Preserve implementation choice by defining how an implementation declares its selected combination and which combinations have demonstrated interoperability.

| ID / priority | Finding and evidence classification | Proposed specification change | What would demonstrate resolution |
| --- | --- | --- | --- |
| ITU-01 / High | **Observed editorial/completeness issue:** Phase 1 snapshot has no numbered release; §6.2/6.3 are incomplete, §6.5 is a placeholder, §7 LVC-3 is “Coming soon.” §7 LVC-1 references §6.4 rows 3–6 although only rows 1–5 exist. | Publish immutable releases/changelog; stable requirement IDs and machine-readable levels/profile applicability; clearly label normative vs informative content. Complete or explicitly defer procurement clauses and repair cross-references. | A release manifest maps each requirement to source text and tests, and validates every cross-reference. Renumbering does not silently change identifiers. |
| ITU-02 / High | **Implementation ambiguity:** §5/§8 list several formats/models/transports; §6.5 does not yet prescribe an interoperable combination. Our valid VC/VP and custom JSON transport do not establish external-wallet compatibility. | Define at least one minimal LVC-3 interoperability profile with exact data-model, proof, identifier-resolution and exchange versions. Add a capability-declaration format and negotiation/failure rules. Do not imply every listed option is mandatory. | Two independent issuer/wallet/verifier stacks pass the same issuance and presentation suite using the declared profile. Unsupported profiles fail clearly. |
| ITU-03 / High | **Governance detail needed:** §4.3 requires historical issuer scope, keys and governed entry/exit, but implementations still need machine-readable decisions and lifecycle rules. | Specify or profile issuer identifiers, credential-type scope, validity intervals, delegation, key history, compromise, deauthorization, closure, anchor distribution and dispute/correction semantics. Define issue-time versus verification-time decisions explicitly. | Published signed example registry/history and vectors for expired accreditation, compromised key, later closure and delegated authority produce consistent decisions across verifiers. Avoid retaining learner records to achieve issuer-history retention. |
| ITU-04 / High | **Policy choice left to implementations:** §6.4 row 3 permits privacy-respecting published artifacts but does not establish a concrete freshness/offline policy. Our 24-hour TTL was arbitrary application policy. | Define cache metadata and policy declaration, acceptable clock skew, first-use bootstrap, outage/expiry behavior, maximum staleness and privacy-safe fetching. Distinguish invalid, revoked, unknown and temporarily unverifiable states. | Shared vectors cover fresh, stale, missing, tampered and rotated artifacts; expired evidence never yields an unjustified acceptance. Offline claims disclose preconditions. |
| ITU-05 / High | **Human assurance gap:** row 4 requires visibility/approval, but a raw JSON payload can satisfy a mechanical gate without usable informed consent. Row 5’s “infer” prohibition cannot be established by a unit test alone. | Add human-readable disclosure guidance, requester authentication, actual-field/purpose matching, accessible/mobile consent examples, request expiry and auditable retention boundaries. Distinguish technical prevention, verifier governance and legal obligations. | Interop tests assert payload-review equivalence and no presentation before approval; usability tests establish comprehension; retention/inference obligations have declared audit evidence and limits. Do not require permanent personal-data consent logs by default. |
| ITU-06 / High | **Semantic interoperability gap:** §5 encourages OB3/CLR/ELM and vocabularies, while detailed schemas remain pending. Our local diploma schema is only a stopgap. | Publish one minimal education profile and validated examples, with extension rules, qualification/issuer identifiers, original-script language handling and mappings that distinguish equivalence from mere similarity. Name schema/vocabulary owners and migration policy. | Positive/negative schema fixtures and a crosswalk explain information loss. Verifiers can distinguish “same title” from recognized qualification under a stated jurisdiction/policy. |
| ITU-07 / Medium | **Test interpretation ambiguity:** §6.4 row 2 contains both “MAY” and “SHALL” under a RECOMMENDED row; vendor neutrality has no concrete external-wallet test protocol yet. | Clarify optional bundle support versus mandatory per-credential behavior when a bundle is accepted. Publish a profile-specific conformance suite with full and partial result classes; include independent receipt and multi-issuer negatives. | An implementation can declare “no bundle support” without ambiguous scoring, while a bundle-supporting verifier must preserve separate issuer/evidence results. Toolkit tests cannot be advertised as consumer-wallet certification. |
| ITU-08 / Medium | **Lifecycle coverage needed:** long-term verification, minors, offline/paper fallbacks and languages are important stated topics but incomplete in §6.3. | Add scoped lifecycle profiles for recovery, correction/reissuance, holder-key change, guardianship, institution closure and archival algorithm/context preservation. Keep LVC-1/2/3 alternatives distinct. | Executable lifecycle scenarios plus governance prerequisites identify what is demonstrated now versus what requires operational evidence over time. A seed export alone is not accepted as proof of secure recovery or decades-long continuity. |

## Cover note for LearnCard

The minimal plugin stack produced genuine VC 2.0 Data Integrity credentials and presentations that a separate Digital Bazaar implementation verified. That is a strong basis for education-sector interoperability. The main improvements we would value are an executable, versioned capability contract, a documented local/mobile storage and recovery boundary, and tested combinations of exchange/credential formats with external wallets. These suggestions address SDK documentation and public API contracts; they do not assume LearnCard defines its own replacement for the W3C or OpenID specifications.

| ID / priority | Finding and evidence classification | Proposed SDK/documentation change | What would demonstrate resolution |
| --- | --- | --- | --- |
| LC-01 / High | **Recorded version-scoped defect:** DIDKit plugin **1.10.3** wraps `issueCredential` with unconditional `JSON.parse`; requesting compact JWT issuance failed in `research/probe.mjs`. Successful Data Integrity signing does not validate the JWT route. | Confirm on a clean minimal reproduction, branch return parsing by actual proof format and document accurate return types. Review presentation paths for the same class of error. | Release tests show compact JWT returned as a compact token and JSON-LD returned as an object, both independently verified; malformed outputs fail with a useful error. State affected/fixed versions. Do not report this as an unfixed current-release bug without rechecking. |
| LC-02 / High | **Observed documentation/source inconsistency:** SD-JWT plugin **0.2.16** README lists holder presentation as future Slice 3, while shipped `present.ts` and tests exist. | Publish a generated per-release matrix: receipt, display, presentation, key binding, status, supported DID methods and protocol/profile versions. Keep experimental versus supported paths explicit. | README, exported APIs and release test results agree for the installed version. Test vectors identify supported and intentionally unsupported combinations. Presence of source alone is not a support guarantee. |
| LC-03 / High | **Integration opportunity:** our independent-library experiments passed, but actual wallet/protocol exchange was not exercised. | Provide a public conformance/interop pack: exact LearnCard dependency stack, offline loaders, W3C signed artifacts, challenges/audiences, schema/status/trust fixtures and named external-wallet exchange recipes. Separate crypto, data model and protocol compatibility. | CI exercises at least one independent verifier and external holder implementation; published wallet-product results name versions, formats and failures. Replays, wrong audience and missing status are included. |
| LC-04 / High | **Application boundary not sufficiently turnkey for our chosen stack:** custom local storage and two incompatible backup envelopes were needed. Native holder-continuity **0.2.21** was researched but not integrated. This is not evidence that native recovery is broken. | Document a browser/mobile persistence adapter contract compatible with holder-continuity: key ownership, import/export, schema versions, migrations, corruption, clean-device recovery, status/trust reacquisition and unsupported custody modes. | A maintained local-only sample exports, wipes and restores on a clean device, preserving identity/proofs without issuer-private records. Provide explicit migration guidance between supported stores; do not promise arbitrary wallet bundle compatibility. |
| LC-05 / Medium | **Recorded dependency friction:** this project’s default optional/mobile dependency graph had five high audit findings; its tested Node-only path had zero at the recorded time. This is a project-lockfile observation, not a blanket vulnerability claim about LearnCard. | Offer clear environment-specific entry points/dependency guidance and a tested Node-only path; keep browser/native extras explicit. Publish dependency/SBOM and advisory triage guidance for supported configurations. | Fresh Node, browser and native sample installs have documented dependency graphs and compatible lockfiles. Reachability/mitigation is stated per advisory; “zero audit” is not represented as complete security assurance. |
| LC-06 / Medium | **Observed onboarding friction:** package examples and source/docs differed in init imports, storage descriptions and feature status. Plugin ordering also affects capability composition. | Run documentation examples against the released packages; generate API references from versioned exports; document plugin ordering, formats and typed errors; keep source docs available as a stable fallback. | CI builds and runs the documented local Node/browser recipe without paid hosted services or undocumented workarounds, and a user can identify the appropriate version of every example. |
| LC-07 / Medium | **Mobile product opportunity, not missing cryptographic standard:** the SDK primitives do not themselves supply an understandable receive/consent/recovery flow. | Provide an accessible mobile reference flow with human-readable disclosure, provenance display, status/unknown-state components, QR/deep-link handoffs and recovery UX. Separate display-only fields from signed/disclosed fields. | Example works on declared real iOS/Android devices, passes manual accessibility review and shows exactly what data is sent. Copy never equates SDK integration with accreditation or ITU conformance. |
| LC-08 / Medium | **Education adapter opportunity:** trust, accreditation and recognition remain application responsibilities; Network APIs were not used in this experiment. | Publish an education-sector integration guide showing supported optional Network adapters versus local/third-party alternatives, historical authority evaluation and independent recognition policy. Include one validated education-model profile. | A reference can swap the status/trust provider without changing credential ownership or collapsing all checks into one boolean. Documentation identifies which behaviors are SDK, hosted-service, partner-governance and application responsibilities. |

## Suggested joint ITU × LearnCard contribution

Create one open, versioned education interoperability kit: a minimal LVC-3 profile, validated diploma/micro-credential fixtures, independently issued/verified examples, signed historical trust/status fixtures, an accessible mobile consent example, and a replay/expiry/privacy test suite. Publish results per implementation/version and profile rather than using a single “standards-compliant” badge.

Start by agreeing the profile and expected outcomes with another wallet/verifier team. Our repository can contribute executable examples and negative cases; it should not be appointed the normative implementation or certification authority.
