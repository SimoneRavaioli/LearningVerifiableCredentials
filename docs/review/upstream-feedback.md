# Proposed feedback to ITU LVC and LearnCard — after Wallet v2

These are draft contributions for discussion, **not issues or messages already sent**. Evidence comes from ITU material retrieved on 14 October 2026, LearnCard repository commit `1de9e4a8aed6a03b9428a6fa7895c9681e50ea7e`, and the named npm releases. Check the latest upstream version and existing issues before filing. Our cloud-preview access failures and our custom backup limitations are primarily our delivery/application responsibilities, not evidence that either upstream specification is defective.

## V2 implementation update — 15 October 2026

The original product is now Wallet v1; [Wallet v2](https://learning-passport-wallet-v2.wellanole256.chatgpt.site/) is separately deployed owner-private. These proposals incorporate its [recorded release](../../v2/evidence/release.json) and [LearnCard protocol test](../../v2/docs/learncard-protocol-status.md), without pretending the upstream ITU draft was freshly retrieved or an upstream change was made. No feedback has been sent.

V2 replaces several v1 application gaps: readable mobile consent, a pinned OB3 application subset, clean-browser holder recovery, multi-issuer UI receipt, isolated local service roles and an unmodified LearnCard OpenID-plugin issuance/presentation round trip. The main UI still shares full credentials; selective disclosure is a separate experimental JOSE module. Consumer-app/device studies, complete education-model certification, institutional trust and production operations remain unproven.

This is evidence for more precise upstream proposals, not evidence that our original application limitations were all upstream defects. SDK interoperability is not consumer-app certification; our custom recovery format is not LearnCard's native bundle format.

## Cover note for ITU

We built an adult learner-held education credential demonstration against the LVC-3 working draft using LearnCard issuance and independent Digital Bazaar verification. The distinction between cryptographic validity, credential status, issuer authority at issuance and recognition policy was especially useful. V2 demonstrates one limited profile with a real SDK client. The continuing obstacle to reproducible ecosystem interoperability is the absence of a fully specified implementation/test profile: independently reasonable choices about education schema, transport, status freshness and trust governance can still produce incompatible systems.

Please consider a small versioned reference profile and executable test pack before expanding the catalogue of options. Preserve implementation choice by defining how an implementation declares its selected combination and which combinations have demonstrated interoperability.

## Cover note for LearnCard

The minimal plugin stack produced genuine VC 2.0 Data Integrity credentials and presentations that a separate Digital Bazaar implementation verified. V2 additionally runs limited final-1 style ldp_vc issuance and PEX ldp_vp/direct_post presentation using unmodified OpenID plugin0.3.11; Digital Bazaar verifies the result. That is a stronger basis for education-sector interoperability, while the complete LearnCard consumer UI/storage/device flow remains untested. The main improvements we would value are an executable, versioned capability contract, a documented local/mobile storage and recovery boundary, and tested combinations of exchange/credential formats with external wallets. These suggestions address SDK documentation and public API contracts; they do not assume LearnCard defines its own replacement for the W3C or OpenID specifications.

## Suggested joint ITU × LearnCard contribution

Create one open, versioned education interoperability kit: a minimal LVC-3 profile, validated diploma/micro-credential fixtures, independently issued/verified examples, signed historical trust/status fixtures, an accessible mobile consent example, and a replay/expiry/privacy test suite. Publish results per implementation/version and profile rather than using a single “standards-compliant” badge.

Use the existing v2 LearnCard SDK fixture as one concrete contribution, then agree expected outcomes with the LearnCard consumer-app team and another wallet/verifier team. Our repository can contribute executable examples and negative cases; it should not be appointed the normative implementation or certification authority.
