# Retrospective and prioritized improvement backlog

## Assessment

The project achieved meaningful technical results: real LearnCard-issued VC 2.0 credentials, distinct signing identities, independent Digital Bazaar verification, explicit consent, signed status and issuer-history checks, and a functioning synthetic workflow. It also exposed the difference between a cryptographic reference implementation and a usable education wallet.

The present experience is a three-role laboratory in one browser. Its visual style is coherent, but its interaction model is aimed at implementers. The learner must understand role switching, credential selection and presentation terminology. The employer result follows several other panels, making the important outcome hard to find on mobile. A readable page at 390 px is useful evidence of responsive layout; it is not evidence of mobile usability, accessibility or native wallet readiness.

Two implementation modes must remain explicit. The Node application stores the learner key under server-side custody and enforces HTTP role boundaries. The static browser preview holds issuer, learner and fictional authority identities at the same origin; its role passwords are a demonstration device. Browser encryption does not isolate these institutions or protect against malicious code served from that origin. Neither mode establishes institutional identity or national accreditation.

## What worked and what to keep

- Preserve independent verification and separate explanations for signature/date validity, status, historical issuer authority and employer policy. This is the clearest substantive product differentiator.
- Keep exact dependency versions, bundled signing-engine integrity checks, signed examples and negative tests. These make a repeatable reference possible.
- Keep explicit approval before presentation, challenge/audience binding and one-use requests. Improve their explanation and states rather than removing the controls.
- Keep the synthetic-data boundary visible. Consolidate technical caveats into a useful “About this demo” view, while retaining warnings next to actions where they affect decisions.
- Keep the private HTTPS preview and a documented local fallback. Access to a preview is part of delivery, not an incidental infrastructure task.

## Criticisms of the project process

| Finding | Why it mattered | Change for the next iteration |
| --- | --- | --- |
| Preview access was tested inside the cloud before a usable user-facing route existed. Repeated queued opens were treated as progress. | The user could read the README but could not experience the product. Local HTTP 200 did not prove delivery. | Start with a minimal page on the actual delivery path; require a user-device smoke test before building the full experience. Treat “queued” as an unverified UI request. |
| Similar file/port attempts continued after the failure boundary was clear. Technical questions were passed back to the user. | The user had to diagnose infrastructure rather than review a wallet. | Time-box a failed delivery route, explain the concrete limitation once, and prepare a working alternative with plain instructions. Ask only for choices that change exposure or cost. |
| A full Node app and browser-local fork now duplicate logic. | Security behavior, schemas and claims can drift. | Share model/verifier modules, specify adapter contracts and run the same behavioral fixtures against both modes. Keep mode-specific custody and network differences explicit. |
| Test summaries and assessments describe different stages. | Older “20 tests,” “no deployment,” and custody statements can be read as current facts. The requirement matrix even calls the verifier “JOSE” although this path uses Data Integrity. | Generate a dated evidence manifest per commit, preserve older results as history, and make the latest assessment reference one manifest. Correct the JOSE attribution. |
| The GitHub export contains source but omits generated ZIPs used by preview download links; packaging scripts contain workspace-specific paths. | A fresh clone is not yet proven to reproduce every feature of the published preview. | Make packaging portable, generate downloads in a documented build step, and verify the clone-to-preview route in CI. |
| The original agent assessment says the build needed no further human intervention. | The complete delivery involved repeated user reports, environment adjustments and hosting approval. | Report research, implementation and delivery separately; count user interventions and failed access attempts in future experiments. |

## Priorities and scope

**P0** blocks a reliable, honest showcase. **P1** establishes a meaningful interoperability PoC. **P2** is needed before a real-user pilot, or extends the product. Effort is relative: S = a focused task, M = several connected changes, L = a cross-component or partner integration. These are planning estimates, not delivery commitments. Product, design, engineering, QA and standards lead are proposed responsibilities, not assigned people.

## Proposed order

1. **Showcase iteration:** UX-01–06, DEMO-01–02, REL-01–02, QA-01–02 and SEC-01. First deliver a short, understandable synthetic demo on the user’s phone and an employer screen.
2. **Interoperability PoC:** agree a wallet partner, profile and education model early; then INT-01–03, DATA-01, SEC-02, REC-01, TRUST-01 and QA-03. Add PRIV-01 if the PoC claims selective disclosure; otherwise disclose its absence prominently.
3. **Pilot preparation:** OPS-01, MOB-01 and LIFE-01, plus independent security/privacy review and jurisdiction-specific governance. A showcase release is not approval to handle real student data.

The first design work should be a clickable mobile learner flow and the human-readable disclosure/result screens. The first engineering work should make builds and demo data reproducible. Avoid adding a native shell before these basic tasks work.
